# ADR-0002: Resposta 202 assíncrona

**Contexto.** O ERP pode ficar lento ou dar timeout. Chamá-lo dentro da requisição HTTP acopla a latência e a disponibilidade da API às do ERP e incentiva o cliente a repetir a chamada justamente quando o ERP está lento, o que aumenta o risco de duplicidade.

**Decisão.** `POST /orders` só valida, persiste o pedido com status `PENDING` (de forma idempotente) e responde `202` com `Location`. O envio ao ERP acontece no worker. O cliente acompanha o pedido por `GET /orders/:id`.

**Consequências.**
- (+) A API responde em milissegundos e continua disponível com o ERP fora do ar. Pedidos aceitos nunca se perdem.
- (+) A repetição do cliente é barata e segura (replay `200` com o estado atual).
- (−) O cliente não recebe o `erpOrderId` na resposta: precisa consultar o status (ou, no futuro, receber um webhook).
- (−) Existe uma janela entre o "aceito" e o "enviado". `NEEDS_REVIEW` exige operação humana.

**Alternativas descartadas.** Chamada síncrona com timeout curto (a resposta HTTP também fica ambígua). Modelo híbrido, que tenta de forma síncrona e cai para o assíncrono se falhar (dois caminhos de código para o mesmo efeito).
